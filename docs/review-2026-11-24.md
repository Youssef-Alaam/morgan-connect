## 2. Contradictions between decisions

### C1. "No account put at risk" (9) vs WhatsApp Cloud API in v1 (40)

Decision 9 is written as a hard rule. The research verdict for exactly our case (an admin running Morgan for their own household or team) is **"Grey, not safely"**, ban risk **medium to high**, and its bottom line is "do not make WhatsApp the default channel... optional adapter that the admin enables at their own risk". Decision 40 took the route but softened the framing to "a clear note".

| Fact from the research                                                                                                              | Why it matters                                                |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Clause 4.7 bars "AI Providers" whose AI is the "primary functionality"; Meta decides "in its sole discretion"                       | A personal assistant is the whole product the chat user gets  |
| Exempt markets: Italy, EU/EEA, Brazil, Turkiye. **Egypt and Saudi Arabia are not listed**                                           | The owner, user #1, is outside the exemption                  |
| A family-only bot is "the weakest fit"; a small business team is the most defensible                                                | Most self-hosters are not registered businesses               |
| The risk lands on the dedicated bot number and the Meta business portfolio, not the admin's personal WhatsApp                       | Damage is contained, but it is still "an account put at risk" |
| Five items still unverified (live wording of 4.7, rate card, verification without a company, newer ToS, a written answer from Meta) | Nothing here is settled law                                   |

Read strictly, 9 forbids 40. Read as the owner probably meant it ("never trick a user into a breach"), an opt-in adapter with an honest warning satisfies it. The spec cannot hold both wordings. **Question Q1.**

### C2. WhatsApp's 24-hour window vs schedules, quiet hours, approvals and login codes (13, 14, 20, 38, 40)

Free-form replies are only allowed within 24 hours of the user's last message. Anything Morgan starts on its own after that needs a Meta-approved **template** and is billed. That hits five decided features:

| Feature                                    | Decision | Problem outside the window                                                 |
| ------------------------------------------ | -------- | -------------------------------------------------------------------------- |
| Scheduled results and daily briefs         | L9, 38   | Needs a utility template; quiet hours push more deliveries past the window |
| Approval request for a long-running job    | 19, 27   | Same                                                                       |
| "Ask for more" top-up message to the admin | 20       | Same, and the admin may not have texted the bot that day                   |
| One-time login code to the linked chat     | 13       | Needs an _authentication_ template                                         |
| Chat-code second factor                    | 14       | Same                                                                       |

Each install has its own Meta portfolio, so each admin must get templates approved themselves. Proposed handling (no decision changed): onboarding creates **one generic utility template** ("You have an update from {bot}. Reply to open it.") and one authentication template; a reply re-opens the window and Morgan then delivers the real content. Telegram, web push and Discord/Slack have no such limit and stay the default for proactive messages.

### C3. Composio as the default (45) vs the privacy pitch, and vs rule 9

Decision 45 already requires a plain disclosure, so this is narrower than it looks. What is left:

- **The word "default".** With Composio preselected, most installs will route Gmail, Calendar and Drive content plus OAuth tokens through a third party, while the README will say "self-hosted". Both are true; the pitch must not say "your data never leaves your server".
- **Composio's own terms were never researched.** We checked 15 model providers and Meta, but not whether Composio's terms allow an end user's personal key inside a third-party self-hosted agent, or what its free tier covers. Under rule 9 that is a research task before the path ships, not an assumption.
- **The owner as user #1.** His mail and Drive include work material, so for his own install the private path (own Google OAuth app) is the right one regardless of the product default.

**Question Q5** (how the default is presented). The terms research goes into the spec as a blocking task.

### C4. Opt-out telemetry (32) vs GDPR, and vs the owner's own position

Decision 32 already limits it to anonymous aggregates. Three things remain:

- "Counts of installs" needs some install identifier, and the collection server sees IP addresses. A stable install ID plus an IP is arguably personal data, which is the opt-in case the decision itself wants to avoid. It stays anonymous only if the ID is random, never linked to anything, and IPs are not stored.
- Someone must run the collection endpoint. That makes the maintainer, a private person, a data controller for EU installs, with a privacy notice to maintain and a server to pay for.
- There is nothing to measure until there are installs.

**Question Q4.**

### C5. One bot per install (22) vs access profiles per user and per device (27, 31)

On a shared bot, Morgan sees a **chat identity** (a WhatsApp number, a Telegram user id), not a physical device. If a younger family member uses the owner's phone with the owner's WhatsApp, Morgan cannot tell them apart. So "device" can only mean one of two things: a linked chat identity, or a signed-in web session/browser. The restricted-device example works only if that person messages from **his own** number or Telegram account, linked with a restricted profile.

This is a definition, not a change, so the spec will adopt it unless the owner objects: _a device is a linked chat identity or a web session; profiles attach to (user, device)_.

Two holes come with it:

- **Workspaces on one bot (21).** A chat message carries no workspace. Proposed: each linked chat has a default workspace and a `/workspace` command switches it.
- **Group chats were never decided.** Discord and Slack are multi-person by nature, and WhatsApp/Telegram groups exist. Whose profile, budget and memory apply when the bot is in a group? Proposed: **v1 is direct messages only** on every channel; groups go on the later list.

### C6. Speed goal (50) vs the safety design and the engines

| Source of delay                                                             | Decision             | Size                                                                |
| --------------------------------------------------------------------------- | -------------------- | ------------------------------------------------------------------- |
| Trust check: one extra model call per gated tool call                       | L7, 30               | To be measured; it is the largest controllable cost                 |
| Bash now goes through the trust check (closing Nod's gap)                   | L6                   | One extra call per command at shell-gate "strict"                   |
| Team mode (boss, managers, workers, boss review)                            | 36                   | Several model calls before the first useful output                  |
| Claude Agent SDK starts a Claude Code process per session, ~100-300 MB each | 16, `loop-engine.md` | Cold start plus memory, on a laptop that Nod alone loads to ~4-6 GB |
| Sandbox container paused when idle                                          | 25                   | Resume time on first use                                            |
| Ask-every-time approvals                                                    | 27                   | A human round trip; unavoidable by design                           |

None of these is wrong, but 50 has no number, so nothing can be tested against it. Proposed targets for the spec _(estimate, to be confirmed by measurement in v0.1)_: Morgan's own overhead on a plain chat turn (no tools) at most 300 ms at the median; a typing indicator or acknowledgement within 1 s on every channel; trust check at most 1.5 s at the median on the fast tier; the trust check runs only for action types the profile sets to "ask" or "auto", never for reads. Team mode is exempt from the texting-speed goal and says so when it starts.

### C7. "Unlimited users" (2) and a container per granted user (25) vs a laptop target (6)

Unlimited accounts are fine; unlimited running sandboxes are not. The log has a per-user parallel-task cap (24) but no install-wide cap and no minimum hardware spec (an open question in L0 that was never closed). Proposed: an install-wide cap on running sandbox and browser containers (default 2 on a laptop profile, admin-editable) with a queue, and a stated minimum spec _(estimate: 4 CPU cores, 8 GB RAM, 20 GB free disk)_.

### C8. "Approvals written once behind one engine port" (16) vs engines that run their own tools

Pi lets us own the tool loop. The Claude Agent SDK, the Copilot SDK and the Cursor SDK are agents with their **own built-in tools** (bash, file edits, web). The Claude Agent SDK exposes a hook before each tool call (`loop-engine.md`: "Trust check becomes a PreToolUse hook"). Whether Copilot's and Cursor's SDKs let us intercept or disable every built-in tool was **not researched**; decision 15 already notes Cursor gives "Cursor's agent rather than raw models".

If an engine can act without passing Morgan's access profiles, the release gate (39, zero unsafe actions) cannot be claimed for it. Proposed rule for the spec: _an engine ships only when every tool call it can make is either routed through Morgan's safety layer or switched off; this is proven per engine by the safety evals._ An engine that cannot meet it is offered as chat-only or not at all.

### C9. Self-service account deletion (48) vs append-only audit log and legal hold (L7, 53)

A user can delete everything; the audit log is append-only; the admin can place a legal hold. Proposed resolution: deletion removes content (chats, memory, files, credentials) and replaces the user's identity in audit rows with a random tag; a legal hold blocks deletion and tells the user so.

### C10. Per-user private memory and data isolation (37, L2) vs the admin console's "knowledge and memory admin", "audit log viewer" and "redacted logs and traces" (49, 53)

Never decided: **can the admin read a member's conversations and memories?** In a family or a small team this is the first question people will ask. **Question Q6.**

### R2. Security

- **Docker control is host root.** The app starts sandbox containers, so it holds the Docker socket. A prompt-injected agent that escapes its container, or a bug in the app, owns the machine, which on the laptop target is the owner's personal computer. Mitigation for the spec: a restricted socket proxy (only create/start/stop of labelled containers), containers without privileges or host mounts, no credentials inside sandboxes, network allowlist by default.
- **An internet-facing login written by a junior developer.** Seven login methods is a wide attack surface. Better Auth covers the standard ones; the two custom ones (chat code, QR login) are where mistakes will be. Core v1.0 defers both.
- **Bootstrap window.** A fresh install on a VPS is claimable by whoever reaches it first; the setup code in the server log (L1) closes this and must be in v0.1, not later.
- **Trust check proves the words exist, not that they cover the action** (verified in Nod's source). Closing this is our own design work with no reference implementation; it needs its own eval set.
- **Connector tokens at rest**, the master key (G7), and the vault's GitHub token with write access are the three secrets whose leak hurts most.
- **Being a maintainer**: a public security policy (`SECURITY.md`, private reporting) is needed on day one of the public repo.

### R3. Terms

- Three grey areas now sit under a rule that says zero: WhatsApp (C1), Composio (C3, unresearched), and any engine route not re-verified (G11).
- The policy file (15) must be re-checked for roughly 15 providers plus Meta and Composio. Terms moved several times in 2026 alone (Anthropic in February and June, Meta in January and October). Proposed: re-check before every minor release, with each route's "last verified" date shown in the admin console and a route auto-disabled when its date is older than 90 days.
- `whatsapp-business-terms.md` and `subscription-terms-others.md` both say their quotes came through a summarising fetch tool and need a re-read on the live pages "before any legal reliance".

### R5. Smaller ones

- **Claude Agent SDK licence**: usable as a dependency but not open source; an Apache 2.0 project that requires it must say so in the README and keep it optional (an install with only Pi must work).
- **Name**: "Morgan Connect" has had no trademark or GitHub/npm name check.
- **Nod marks**: borrow code under Apache 2.0, never the Nod or n8n names or logos, and keep NOTICE.
- **Cost of the safety evals**: Nod's full suite costs about $500 a run (`nod-reference/19`). Ours must be sized to the owner's monthly API credits, which also have to cover daily use.
