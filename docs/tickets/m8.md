# Tickets: M8 (Remaining channels and logins, 1.2)

Status: draft for the owner's review, 2026-11-28. Tickets are disposable: when the spec changes, close the unbuilt ones and regenerate.

Every ticket is a vertical slice: when it is merged, something new can be shown working. Every ticket follows `STANDARDS.md` (tests first, all CI checks green, one PR, at most 400 changed lines). "Tests first" lists the failing tests the builder writes before any code. A ticket too big for one PR is split into lettered parts (a, b, c), each its own PR of at most 400 lines, merged in order. Library names marked _(proposed)_ are not decided until the owner approves them.

Milestone goal (spec section 6): Discord, Slack, magic link, Google/GitHub sign-in, chat-code login and second factor, QR login (D11-D14, D23, D61). No separate "done when" is written in the spec; these tickets use: a person can use each channel and each login, the chat can never be both factors, and the isolation and policy tests pass on every new door.

What already exists and is built on here: the channel adapter port, Telegram and WhatsApp adapters, linking by one-time code, direct messages only (A2); Better Auth with password, TOTP, backup codes and passkeys; the login history (M6-5b); the WhatsApp authentication template (M5-3c).

## M8. Remaining channels and logins

### M8-1. Discord

#### M8-1a. The adapter, direct messages only

- **Blocked by:** nothing in M8.
- **Demo:** the admin adds a Discord bot token; a linked person DMs the bot and gets a reply; a message in a server channel is ignored.
- **Tests first:** the adapter maps DMs to the one message format; guild messages are dropped (A2) and a test asserts it; unlinked senders are ignored; outbound retries three times (G3); typing indicator within 1 s (C6) on the fake gateway; recorded fixtures, no network.
- **Work:** `src/channels/discord.ts`; the bot token in the M4-1c install secrets; the channels page row.

#### M8-1b. Linking and approvals on Discord

- **Blocked by:** M8-1a.
- **Demo:** a person links with a one-time code; an approval arrives with Approve and Deny buttons and works once.
- **Tests first:** linking as on Telegram (story 13); buttons carry the approval id only, and the exact-argument and use-once rules hold; a Discord-linked device gets its own access profile (C5).
- **Work:** the button handling; the link flow.

### M8-2. Slack

#### M8-2a. The adapter, direct messages only

- **Blocked by:** nothing in M8.
- **Demo and tests:** as M8-1a, for a Slack app in one workspace; request signatures are verified and a replayed request is refused.
- **Work:** `src/channels/slack.ts` on `@slack/bolt` _(proposed)_.

#### M8-2b. Linking and approvals on Slack

- **Blocked by:** M8-2a.
- **Demo and tests:** as M8-1b, with Slack's interactive messages.
- **Work:** the interaction handler; the link flow.

### M8-3. Magic link sign-in

- **Blocked by:** nothing in M8.
- **Demo:** on the sign-in page a person enters their email and gets a link that signs them in once, within 15 minutes; a second factor is still asked if they have one.
- **Tests first:** the link is single-use, expires, and is bound to the browser that asked (_proposed_, doubt 2); the response does not reveal whether the email exists; rate-limited per address; recorded in login history; the admin can switch the method off.
- **Work:** Better Auth's magic-link plugin; the SMTP setting (install-wide; the password in the M4-1c install secrets).

### M8-4. Google and GitHub sign-in

#### M8-4a. Google sign-in

- **Blocked by:** nothing in M8.
- **Demo:** "Sign in with Google" signs in an existing person whose email matches a verified link; a new email cannot create an account without an invite (D11).
- **Tests first:** linking a Google identity to an account requires being signed in first; an unlinked Google account is refused with "Ask your admin for an invite."; the second factor still applies; the OAuth app is the install's own (shared with M4-8a's client where scopes allow).
- **Work:** the Better Auth provider; the link screen in settings.

#### M8-4b. GitHub sign-in

- **Blocked by:** M8-4a.
- **Demo and tests:** as M8-4a, for GitHub.
- **Work:** the provider; the admin's OAuth app setting.

### M8-5. The chat code

D13, D14: the chat can never be both factors.

#### M8-5a. Sign in with a code sent to my linked chat

- **Blocked by:** nothing in M8.
- **Demo:** on the sign-in page a person chooses "Send me a code in Telegram", gets a six-digit code in their linked chat and signs in with it.
- **Tests first:** the code is single-use, expires in 5 minutes and is rate-limited; it goes only to a linked chat of that person; on WhatsApp outside the 24-hour window it uses the authentication template (C2); a chat-code sign-in still asks for a second factor that is not the chat: TOTP or a passkey only, never a backup code (D14; a backup code is the lost-phone recovery path, not a factor after the chat).
- **Work:** the code flow in `src/identity`; the sign-in option.

#### M8-5b. The chat code as a second factor

- **Blocked by:** M8-5a.
- **Demo:** a person who signed in with a password can use a chat code as the second factor.
- **Tests first:** a table test over every pair of factors: the chat code is accepted as the second factor only after a password; it is refused after a chat-code sign-in, a magic link, Google, GitHub or QR sign-in (none of those is a knowledge factor, and the chat can never be both factors); the admin's "force 2FA" accepts it only if the admin allows chat codes as a factor (_proposed_, doubt 3).
- **Work:** the factor in the second-factor step.

### M8-6. QR login

- **Blocked by:** M8-5a.
- **Demo:** the sign-in page shows a QR code; a person already signed in on their phone scans it and approves, and the desktop is signed in.
- **Tests first:** the QR carries a one-time id that expires in 2 minutes; approval needs the phone session to be fully signed in (both factors); the desktop gets a new session recorded as its own device; a scanned code shows the desktop's device type and browser before approval, with no IP geolocation (consistent with M6-5b, no IPs stored); replay is refused.
- **Work:** the QR endpoint and approval screen; `qrcode` _(proposed)_.

### M8-7. The channels and logins demo and the M8 report

- **Blocked by:** every ticket above.
- **Demo:** the owner talks to Morgan on Discord and Slack, approves an action on each, and signs in by magic link, Google, GitHub, chat code and QR; tag `v1.2.0`.
- **Tests first:** one integration scenario per new channel and per new login on fakes, asserting isolation, the access profile per device and the "never both factors from the chat" rule.
- **Work:** the scenarios; `docs/m8-report.md` in the shape of `docs/m1-report.md`: timings per ticket, spend, typing-signal time per channel.
- **Done when:** every new door works, the isolation and policy tests pass on all of them, and the report is merged.

## Doubts for the owner

1. **No "done when" in the spec for M8.** The tickets propose the one above.
2. **Magic link bound to the asking browser** _(proposed)_: safer against forwarded mails, but a link opened on another device fails. Say which.
3. **Chat code under "force 2FA"** _(proposed)_: allowed only if the admin allows it, since a lost phone loses both the chat and the authenticator.
4. **Email sending.** Magic links need SMTP; the spec lists "network and email settings" in the full console (D53). M8-3 adds the minimum setting now.
5. **Discord and Slack licences** need the licence check on the chosen packages.
