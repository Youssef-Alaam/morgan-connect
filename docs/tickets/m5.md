# Tickets: M5 (Second engine, router, WhatsApp)

Status: draft for the owner's review, 2026-11-28. Tickets are disposable: when the spec changes, close the unbuilt ones and regenerate.

Every ticket is a vertical slice: when it is merged, something new can be shown working. Every ticket follows `STANDARDS.md` (tests first, all CI checks green, one PR, at most 400 changed lines). "Tests first" lists the failing tests the builder writes before any code. A ticket too big for one PR is split into lettered parts (a, b, c), each its own PR of at most 400 lines, merged in order. Library names marked _(proposed)_ are not decided until the owner approves them.

Milestone goal (spec section 6): the same safety evals pass on both engines and a WhatsApp conversation works across the 24-hour window. Contents: the Claude Agent SDK on an API key under the engine rule (C8), tiers and team mode (D36), fallback (G3), the WhatsApp Cloud API opt-in adapter with the risk notice, setup guide and templates (D40, D55, C2), the PWA with push (D34), workspaces with `/workspace` (D21, A3).

What already exists on `main` and is built on here: the engine port (`open / prompt / steer / abort / usage`) with the Pi and HTTP adapters and a contract test (`src/providers/engine.contract.test.ts`); the retry step (`src/core/retry.ts`); the channel adapter port and Telegram (`src/channels/`); `workspaces` with one default workspace and `workspace_id` on every user-data table (migration 0010); the `routes` table. From M3 and a hard dependency where noted: the terms policy file (M3-2a), the `pi-only` CI job and the optional-import check (M3-1), the holdout set and the release gate over a list of engines (M3-12c, M3-12d).

Spec section 10 checks that block parts of this milestone: whether the Claude Agent SDK lets us intercept or disable every built-in tool (first result: a pre-tool hook can gate it, `research/sdk-tool-interception.md`); Meta clause 4.7, the country list, the written question to Meta and the Egypt rate card (WhatsApp).

## M5. Second engine, router, WhatsApp

### M5-1. The Claude Agent SDK, under the engine rule

Split into three PRs. C8: an engine ships only when every tool call it can make is routed through L7 or switched off, proven by the safety evals for that engine.

#### M5-1a. The adapter behind the engine port, chat only

- **Blocked by:** M3-1.
- **Demo:** with `ENGINE=claude-sdk` and an Anthropic API key, the owner texts and gets a reply; every built-in tool of the SDK is switched off, so the engine is chat-only for now.
- **Tests first:** the adapter passes the engine contract test on a recorded fixture of the SDK's stream (no network); the SDK is an optional dependency, imported only from its adapter folder, and the `pi-only` job still passes with it left out; with the package missing, `ENGINE=claude-sdk` fails at boot with a plain sentence; the allowed-tools list passed to the SDK is empty and a test asserts it; usage reaches the ledger with input, output and cache tokens; the route is a row in the policy file and an expired route refuses; the licence check accepts the package or the PR stops (doubt 1).
- **Work:** `src/providers/claude-sdk/` (adapter); `optionalDependencies` entry; the route row; the config value.

#### M5-1b. Our tools through the pre-tool hook

- **Blocked by:** M5-1a.
- **Demo:** on the Claude SDK engine, "capture this" asks for approval exactly as on Pi; a tool call the SDK tries outside our registry is refused and logged.
- **Tests first:** our registry's tools are offered to the SDK and every call reaches `src/policy/gate.ts` through the SDK's pre-tool hook; a call to any tool name not in our registry is denied by the hook and writes an audit row (`decision: 'refused'`, reason "built-in tool"); sub-agents, if the SDK spawns them, inherit the same hook or are switched off (a recorded fixture with a sub-agent call proves it); a hook error denies (fail closed); the gate's audit and fence rules hold as on Pi.
- **Work:** the hook in the adapter; the built-in deny list; the test fixtures.
- **Out of scope:** any SDK built-in tool being switched on (each needs its own ticket and evals).

#### M5-1c. The safety evals on both engines

- **Blocked by:** M5-1b, M3-12d.
- **Demo:** the `release-gate` workflow runs the holdout set on Pi and on the Claude SDK engine and prints one table per engine.
- **Tests first:** the engine list the release gate reads includes `claude-sdk` only when the optional package is installed; a run on one engine cannot pass the gate for the other; the dev set runs on both with `--engine`.
- **Work:** the engine entry in the gate list; the `--engine` flag in the evals CLI; the eval spend cap sized for two engines.

### M5-2. Tiers, fallback and team mode

Split into four PRs. D36: fast / strong / boss tiers per provider profile; one agent first, escalating to team mode for big jobs or `/team`; no separate classifier.

#### M5-2a. Provider profiles with three tiers

- **Blocked by:** nothing in M5.
- **Demo:** the admin's provider profile names a model for each of fast, strong and boss; a person's default tier is strong; `/model fast` switches their chat to the fast tier.
- **Tests first:** a profile is validated at load (each tier names a model on an allowed route); a person's preferred tier and model are per person and per chat (RLS); the engine opens with the chosen tier's model; an unknown tier or a model on an off route is refused with a plain sentence.
- **Work:** provider profiles in config (install-wide, exempt list); the person's preference columns; the `/model` command.

#### M5-2b. Fallback within a tier

- **Blocked by:** M5-2a.
- **Demo:** with the strong tier's first model failing, the turn retries twice, then answers on the tier's second model, and the reply says which model answered.
- **Tests first:** G3 as a table test on the fake engine: two retries with backoff on transient errors, then the next model in the tier, then one plain sentence to the person; a non-transient error (auth, route off) skips retries; a turn that has already run a changing tool never falls back (it would repeat the action); the usage ledger records the model that answered.
- **Work:** the fallback list per tier; the step in `src/core/retry.ts`.

#### M5-2c. `/team` runs a boss, managers and workers

- **Blocked by:** M5-2b.
- **Demo:** `/team plan a three-day trip to Luxor` says "This will take longer." and runs a boss that plans, managers that each own one part and split it, workers that each answer one piece, and the boss that reviews and replies once (D36).
- **Tests first:** team mode is one job with child turns, each with its own idempotency key, all under the person's budget and parallel-task cap; every child's tool call passes the same gate with the person's profile (a worker cannot do what the person cannot); the boss uses the boss tier, managers the strong tier and workers the fast tier _(proposed)_; a manager reports only to the boss and never replies to the person; an abort stops every child; the speed targets are exempt and the start message says so (C6).
- **Work:** `src/core/team.ts`; the child-turn job; the `/team` command; the start message as a translation key.

#### M5-2d. Morgan escalates by itself

- **Blocked by:** M5-2c.
- **Demo:** asked for a large job without `/team`, the single agent calls an `escalate` tool, the person is told it will take longer, and team mode runs.
- **Tests first:** escalation is a tool the model calls, not a classifier (D36); it is a `read`-type internal action and does not call the safety model; it can happen at most once per turn; a person whose profile or budget does not allow team mode gets a plain sentence and the single agent carries on.
- **Work:** the `escalate` tool; the profile switch for team mode.

### M5-3. WhatsApp Cloud API, opt-in

Split into four PRs. D40, D55, C2.

#### M5-3a. The risk notice and the switch

- **Blocked by:** nothing in M5.
- **Demo:** the providers and channels page shows WhatsApp as off and grey; switching it on shows the risk notice, and only after the admin ticks "I have read this" and confirms is it on; the acceptance is in the audit log.
- **Tests first:** the WhatsApp route is `grey` in the policy file and off without a recorded opt-in (spec section 4 Terms rule); the notice text is a translation key whose content is snapshot-tested; acceptance stores who, when and the notice version, and a new notice version requires a new acceptance; Playwright: the switch cannot turn on without the tick. Story 12.
- **Work:** the notice; the switch on the M2-15e page; the acceptance row (install-wide, exempt list).

#### M5-3b. The adapter: webhooks in, messages out

- **Blocked by:** M5-3a, the spec section 10 Meta check.
- **Demo:** a message to the install's WhatsApp number from a linked person reaches Morgan and the reply arrives in WhatsApp; an unlinked number is ignored.
- **Tests first:** the webhook verifies Meta's signature and refuses an unsigned or replayed call; the verify-token handshake works; incoming messages map to the one message format; linking by one-time code works as on Telegram (story 13); outbound sends retry three times (G3); recorded fixtures, no network in tests; the adapter does nothing while the switch is off.
- **Work:** `src/channels/whatsapp.ts`; the webhook route; the number id in config; the token and app secret in the M4-1c install secrets.

#### M5-3c. The 24-hour window and the two templates

- **Blocked by:** M5-3b.
- **Demo:** a schedule result due 30 hours after the person's last message is sent as the generic template "You have an update from {bot}. Reply to open it."; the person replies and the real result arrives.
- **Tests first:** with a fake clock, a send inside 24 hours of the person's last message is free-form; outside it, the held content is stored and the utility template is sent instead; a reply delivers held items in order; a login code or chat-code factor outside the window uses the authentication template (C2); quiet hours still apply before the template is sent; template names and languages come from config.
- **Work:** the window tracker; the held-content queue (shared with M4-4b where it fits); the template sends.

#### M5-3d. The setup guide

- **Blocked by:** M5-3c.
- **Demo:** `docs/guides/whatsapp.md` takes an admin from no Meta account to a working number: business portfolio, dedicated number, app, webhook, the two templates to submit, and the AI-provider clause note.
- **Tests first:** a docs check that every config key named in the guide exists in the config schema and every config key the adapter reads is named in the guide; the guide links the research note and the date it was checked.
- **Work:** the guide; a link from the channels page.

## Doubts for the owner

1. **The Claude Agent SDK's licence.** It is not open source (A13). The licence check allows only listed licences; it needs an explicit exception for one optional package, or the check must skip `optionalDependencies`. The owner's call.
2. **The Meta check is not done.** M5-3b waits on spec section 10 (clause 4.7, the country list, the written question, the Egypt rate card). M5-3a can land first since the switch is off.
3. **Team mode cost.** No cap on child turns per job is in the spec; M5-2c proposes the person's budget and parallel-task cap as the only limits. Say if a per-job cap is wanted.
4. **Push content** _(proposed)_: a title only, no message text, because push goes through browser vendors' servers. Say if a preview is wanted.
5. **Workspace roles.** The spec names admin and member only; M5-5b gives each membership a role but adds no new role.
6. **Held content in two places.** Quiet hours (M4-4b) and the WhatsApp window (M5-3c) both hold messages; they should share one queue if M4-4b's shape allows.
