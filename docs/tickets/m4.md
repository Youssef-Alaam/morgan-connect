# Tickets: M4 (The owner's daily driver)

Status: draft for the owner's review, 2026-11-28. Tickets are disposable: when the spec changes, close the unbuilt ones and regenerate.

Every ticket is a vertical slice: when it is merged, something new can be shown working. Every ticket follows `STANDARDS.md` (tests first, all CI checks green, one PR, at most 400 changed lines). "Tests first" lists the failing tests the builder writes before any code. A ticket too big for one PR is split into lettered parts (a, b, c), each its own PR of at most 400 lines, merged in order. Library names marked _(proposed)_ are not decided until the owner approves them.

Milestone goal (spec section 6): the owner has used it daily for a week in place of his current setup and the morning brief arrives on schedule. Contents: vault connector in full (G8, A9), memory with the suggestion rules of story 19 (D37, D62), schedules and quiet hours (D38), voice notes in (D41), connectors: Composio after its terms check (spec section 10), MCP, own Google OAuth with the choice screen (D45, D58, C3).

What already exists on `main` and is built on here: the vault capture tool that writes one new file in `_inbox/` as one commit (`src/tools/vault.ts`, `vault-capture.ts`); the policy gate, approvals bound to exact arguments, the audit log and the usage ledger; conversations with `/new` and compaction (`src/core/compaction.ts`, `src/data/compaction.ts`); `withOwner` and row-level security on every user-data table; the `routes` table (migration 0041) and the web console. From M3 and a hard dependency where noted: the trust check before every gated action (M3-4c), `Untrusted` tool results by type (M3-6), files (M3-10), fake worlds for evals (M3-12a). `src/cadence` is an empty module today.

## M4. The owner's daily driver

### M4-1. The per-person credential vault

Split into two PRs. Spec L3: credentials are envelope-encrypted, one person each, never shared (D15, D18). Nothing on `main` stores a third-party secret yet, and M4-5, M4-7, M4-8 and M4-9 each need one.

#### M4-1a. The master key file and envelope encryption

- **Blocked by:** nothing.
- **Demo:** a fresh install creates a master key file outside the database at boot; `sealSecret` and `openSecret` round-trip a value; a database dump shows only ciphertext.
- **Tests first:** boot creates the key file with owner-only permissions when absent and refuses to start when the file is present but unreadable or the wrong length; each secret gets its own data key, wrapped by the master key (AES-256-GCM through `node:crypto`, no new package); a tampered ciphertext, a wrong key or a swapped data key fails to open with a typed error, never a garbled value; the master key path is in the config schema and is never logged (redaction test); the key file is written temp-then-rename (`src/ops/atomic-write.ts`).
- **Work:** `src/ops/master-key.ts`, `src/safety/envelope.ts` (pure functions); config key `MASTER_KEY_FILE`; a warning line in the setup log telling the admin to store the key separately (A8, G7).

#### M4-1b. The `credentials` table, one owner per row

- **Blocked by:** M4-1a.
- **Demo:** a person saves a credential (kind, label, sealed value) through the API; only that person's own tools can open it; the admin's console lists that it exists but never shows its value.
- **Tests first:** `credentials` carries `user_id` and `workspace_id` under RLS with an isolation test (the checker in `scripts/check-isolation-tests.mjs` passes); reading a credential for another person fails even for the admin; listing returns kind, label, created and last-used dates, never the value or the ciphertext; deleting a credential writes an audit row; a test fails if any HTTP response body contains a sealed or opened value (fixture scan, like the M2-15e key test).
- **Work:** the migration (next free number); `src/data/credentials.ts`; `src/http/credentials.ts` (save, list, delete); no UI beyond what M4-5, M4-8 and M4-9 add.
- **Out of scope:** a member's own model-provider key (story 18) and key rotation of the master key (doubt 2).

#### M4-1c. Install-wide sealed secrets, on the exempt list

- **Blocked by:** M4-1a.
- **Demo:** the admin saves an install-wide secret (for example the Google OAuth client secret) through the admin API; the app opens it where it is needed; the console shows that it is set and when, never its value.
- **Tests first:** `install_secrets` has a fixed set of kinds (Google OAuth client secret, WhatsApp app secret and token, VAPID private key, safety-model key, SMTP password, channel bot tokens) and refuses any other kind; values are sealed with M4-1a's envelope; the table has no `user_id`, is on the RLS exempt list, and the isolation checker passes with it listed; only an admin may write or replace a secret, and each write writes an audit row without the value; the API and logs never return or print a value (fixture scan); a secret set in config at boot is imported once and the config value is then ignored with a warning (_proposed_, doubt 10).
- **Work:** the migration; `src/data/install-secrets.ts`; `src/http/install-secrets.ts` (set, list, replace). M4-8a, M5-3b, M5-4b, M6-1b and M8 store their install-wide secrets here.

### M4-2. The vault connector in full

Split into three PRs. G8 and A9: a fine-grained token for one repo, the server's own clone, new files only in `_inbox/`, a path deny list.

#### M4-2a. The server's own clone, pulled on a timer and before each read

- **Blocked by:** nothing in M4.
- **Demo:** with `VAULT_REPO` and a fine-grained token set, the server clones the repo into its data folder on first use, pulls every N minutes and before each vault read, and `/vault status` shows the last pull time and commit.
- **Tests first:** against a local bare repo in a temp folder: first use clones, later uses fetch and fast-forward; a pull that cannot fast-forward (history rewritten upstream) re-clones into a new folder and swaps it in with a rename, never leaving a half-written clone; two workers pulling at once do not corrupt the clone (a Postgres advisory lock); the token never appears in a log line, an error message or the clone's `.git/config` (credential passed per command); a pull failure leaves the last good clone readable and says so in `/vault status`.
- **Work:** `src/tools/vault-clone.ts`; config keys for the repo, token and pull interval; the `/vault status` command. Existing `vault.capture` moves onto the shared clone.

#### M4-2b. Read and search by the vault's own pointer chain

- **Blocked by:** M4-2a, M3-6.
- **Demo:** "what's on my dashboard?" makes Morgan read `CLAUDE.md`, follow its pointer to the dashboard, and answer from it; "find my notes on the garden project" runs a text search and answers with the file names it used.
- **Tests first:** `vault.read(path)` and `vault.search(query)` are `read` actions (no trust check, C6); every text returned is `Untrusted`; paths resolve inside the clone and `..`, absolute paths, symlinks out of the clone and `.git/` are refused; search returns at most N hits with path and a short snippet, ranked by match count, and is bounded in time; a `[[wikilink]]` in a read note is resolved to its file by the vault's filename rule so the model can follow it; the start file is a setting on the vault connection, default `CLAUDE.md`, and the system prompt tells the model to start there (a trusted string built from the setting, snapshot-tested with the default and a custom file); a start file missing from the clone is reported by `/vault status`, not silently skipped.
- **Work:** `src/tools/vault-read.ts`, `vault-search.ts` (search over the clone with a plain scan, no index in M4); the `start_file` column on the vault connection; the start-here prompt line. Story 28.

#### M4-2c. The path deny list and write zones

- **Blocked by:** M4-2b.
- **Demo:** with `private/` on the connection's deny list, "read my private journal" is answered with "That folder is switched off for Morgan." and no file is read; a capture still lands in `_inbox/` as one commit.
- **Tests first:** the deny list is a list of path prefixes per connection, checked before every read, search hit and write (a denied file never appears in a search snippet); writes are new files only, in `_inbox/` or a listed write zone (D28), and an existing path is refused (story 29: no existing note is ever edited); a push that loses a race pulls and retries up to three times, then tells the user, and never force-pushes; each write is one commit; the deny list change writes an audit row.
- **Work:** the deny list and write zones as columns on the vault connection (per person, RLS); the checks in the vault tools; the admin API. Which folders are on the owner's own deny list is his call (G8, doubt 3).

### M4-3. Memory

Split into five PRs. D37, D62 and story 19: explicit saves, suggestions only on yes, at most one per conversation, at the end of a reply, an offer before old context is dropped, quote-backed, per person, editable.

#### M4-3a. "Remember this" saves a quote-backed note

- **Blocked by:** nothing in M4.
- **Demo:** "remember that I take my coffee black" saves a note at once and Morgan says so; in a new chat, "how do I take my coffee?" is answered from the note.
- **Tests first:** `memories` carries `user_id` and `workspace_id` under RLS with an isolation test; each row stores the note text and the person's own words it came from (the quote must be found in their own messages, reusing `findQuote` from M3-4a); `memory.save` is a `create` action whose quote is the person's "remember" message, so it passes the trust check without an approval question under the Standard profile (_proposed_, see doubt 4); saved notes are put into the system prompt of each new conversation as `Untrusted` text, capped at N tokens, newest first; a member's notes never reach another person's prompt.
- **Work:** the migration; `src/data/memories.ts`; `src/tools/memory.ts`; the prompt step in `src/core`.

#### M4-3b. Morgan suggests a memory, at most once per conversation

- **Blocked by:** M4-3a.
- **Demo:** after "I moved to Cairo last month", the reply ends with "Want me to remember this for later chats?"; "yes" saves it, "no" or silence saves nothing; a second durable fact in the same conversation brings no second question.
- **Tests first:** the suggestion is a field in the model's structured reply, rendered by Morgan at the end of the reply, never in the middle of a tool run (a turn with a pending approval carries no suggestion); a per-conversation flag allows one suggestion, and `/new` resets it; a save happens only on an explicit yes to that suggestion (a "yes" to anything else does not save); the suggested text and its quote are stored with the pending question so the yes saves exactly what was shown.
- **Work:** the suggestion field in the reply schema; the flag on `chat_conversations`; the yes/no handling in `src/core`; the reply text as a translation key.

#### M4-3c. An offer before old context is dropped

- **Blocked by:** M4-3b.
- **Demo:** in a long chat, before compaction drops the oldest part, Morgan asks once "Before I drop the start of this chat, want me to keep anything from it?" and lists up to three candidate notes; the answer saves the chosen ones.
- **Tests first:** the offer runs before the compaction step that drops messages, not after; it counts as the conversation's one suggestion if none has been made, and is skipped silently if compaction would drop nothing durable (the model returns an empty list); candidates carry quotes from the part being dropped; nothing is saved without a yes; compaction still runs whether or not the person answers (a timeout does not block the chat).
- **Work:** the hook in `src/core/compaction.ts`; the candidate prompt as `trusted()` text.

#### M4-3d. Memory evals

- **Blocked by:** M4-3c, M3-12a.
- **Demo:** `npm run evals -- --suite memory --set dev` runs the spec section 7 memory scenarios and prints a table.
- **Tests first:** the four scenario kinds from spec section 7, at least five each: a durable fact brings a suggestion; a passing remark does not; never two suggestions in one conversation; never a save without a yes; judged on the `memories` rows after the run, not on the reply text; a test fails if a kind has fewer than five scenarios.
- **Work:** the `memory` suite and its scenarios (drafted by the reviewer, spec section 8).

#### M4-3e. `/notes` and the "notes about me" page

- **Blocked by:** M4-3a, M2-13b.
- **Demo:** `/notes` lists the person's notes with numbers; `/notes delete 3` deletes one; the web page lists, edits and deletes them.
- **Tests first:** both views show only the person's own notes (isolation); an edit keeps the original quote and records the edit date; a delete removes the row and writes an audit row; Playwright: edit and delete on the page; screenshot tests in light, dark and right-to-left.
- **Work:** the command in `src/core/commands.ts`; the API in `src/http`; the page with design-system components.

### M4-4. Schedules and quiet hours

Split into three PRs. L9: Nod's schedule engine lifted onto pg-boss, per person, quiet hours, a budget check before each run.

#### M4-4a. A person's schedule runs a prompt on time

- **Blocked by:** nothing in M4.
- **Demo:** "every weekday at 7:30 tell me today's date and the weather in Cairo" creates a schedule; at 7:30 in the person's time zone a turn runs and the reply arrives in their chat.
- **Tests first:** `schedules` carries `user_id` and `workspace_id` under RLS with an isolation test; each has a cron expression, a time zone (IANA, validated) and a prompt; with a fake clock, the next run is computed in the person's zone, including a daylight-saving change; a run is a normal turn with its own idempotency key (G3), so two workers never run the same slot twice; creating a schedule is a `create` action through the gate; a person's schedules stop when their account is suspended.
- **Work:** the migration; `src/cadence/schedules.ts` (lifted from Nod where it fits, NOTICE kept, changes marked); the pg-boss job; the `schedule.create`, `schedule.list`, `schedule.delete` tools.

#### M4-4b. Quiet hours hold results until morning

- **Blocked by:** M4-4a.
- **Demo:** with quiet hours 23:00-07:00, a schedule result at 02:00 is held and delivered at 07:00; a result the schedule marks urgent arrives at once.
- **Tests first:** quiet hours and time zone are per person, editable by `/quiet`; held results are stored, delivered in order at the end of quiet hours, and survive a restart; "urgent" is a flag on the schedule set by the person, never chosen by the model (_proposed_, doubt 5); approval questions raised by a scheduled run during quiet hours wait with the result, and their expiry starts at delivery.
- **Work:** the quiet-hours columns on the person; the hold queue in `src/cadence`; the `/quiet` command.

#### M4-4c. A budget check before each run

- **Blocked by:** M4-4b.
- **Demo:** a person at their spending limit gets "Your 7:30 schedule did not run: you have reached this month's limit." instead of a run, and the "ask for more" button.
- **Tests first:** the budget is checked before the turn starts, using the M2 budget path; a skipped run writes an audit row and does not retry; the person is told once per schedule per day, not every run; schedules on the person's own subscription key are never blocked by the admin-key budget (D46).
- **Work:** the check in the schedule job; the skip message as a translation key.

### M4-7. The connector frame and MCP

Split into two PRs. Every connector action passes the safety layer (spec section 4 Connected apps).

#### M4-7a. One connector port, every action through the gate

- **Blocked by:** M4-1b, M3-4c.
- **Demo:** a fake "notes app" connector offers `notes.list` (read) and `notes.post` (send); `notes.post` asks for approval with the exact arguments, and the result comes back fenced.
- **Tests first:** a connector declares each action with its action type, target field and argument schema, and is registered into the tool registry only through the port; an action without a declared type is refused at registration; every connector result is `Untrusted`; connector tokens are read from the credential vault of the person running the turn only; a connector is per person, so one person's connection is invisible to another (isolation test on `connections`).
- **Work:** `src/tools/connectors/port.ts`; the `connections` table (RLS); the fake connector in `test/`.

#### M4-7b. Connect an MCP server and list its tools

- **Blocked by:** M4-7a.
- **Demo:** the owner adds an MCP server URL (or a local command the admin allows); the connection shows as connected with its list of tools, all `off` until mapped.
- **Tests first:** connect, list and error against a test MCP server in the test folder; only HTTP-based MCP servers are allowed for members, local commands only for the admin (_proposed_, doubt 7); tool descriptions are stored as `Untrusted`; the connection is per person (isolation); the licence of `@modelcontextprotocol/sdk` passes the licence check.
- **Work:** `src/tools/connectors/mcp.ts` (connect and list) on `@modelcontextprotocol/sdk` _(proposed)_.

#### M4-7c. Map MCP tools to action types and call them

## Doubts for the owner

1. **M3 is not finished.** M4-2b, M4-7a and M4-3d wait on M3-6, M3-4c and M3-12a; M4-3e waits on M2-13b. If those shapes change, the tickets need a refresh.
2. **The credential vault is not in the M4 list** but spec L3 requires it and nothing on `main` stores a third-party secret yet, so it is placed first (M4-1). Master key rotation is in no milestone; proposed for M6 security settings.
3. **The owner's own deny list** is his call (G8). M4-2c builds the mechanism; the folders are set by hand at install.
4. **"Remember this" without an approval question** _(proposed)_: a save quoted from the person's own "remember" message passes the trust check and is `auto` under Standard and Trusted. Say if saves should ask.
5. **"Urgent" in quiet hours** _(proposed)_: set by the person on the schedule, never by the model. Say if the model may mark a result urgent.
6. **Speech-to-text provider.** D41 names OpenAI, Google and ElevenLabs; M4-5 builds one adapter. Which one first, and its terms row, needs choosing before it merges.
7. **Local MCP servers** _(proposed)_: members get HTTP MCP servers only; a local command runs on the host, so only the admin may add one. Say if local MCP should run inside the person's sandbox instead.
8. **Morning brief contents.** Story 32 does not say what the brief holds; M4-6 proposes the vault dashboard plus today's calendar.
9. **"Used daily for a week"** is judged by the owner, not by a test; the report records it.
10. **Config secrets moving into the table** _(proposed)_: a secret set by environment variable at boot is imported once into M4-1c. Say if config should stay the source instead.
