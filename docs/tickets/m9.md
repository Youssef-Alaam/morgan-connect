# Tickets: M9 (Full console, 1.3)

Status: draft for the owner's review, 2026-11-28. Tickets are disposable: when the spec changes, close the unbuilt ones and regenerate.

Every ticket is a vertical slice: when it is merged, something new can be shown working. Every ticket follows `STANDARDS.md` (tests first, all CI checks green, one PR, at most 400 changed lines). "Tests first" lists the failing tests the builder writes before any code. A ticket too big for one PR is split into lettered parts (a, b, c), each its own PR of at most 400 lines, merged in order. Library names marked _(proposed)_ are not decided until the owner approves them.

Milestone goal (spec section 6): branding and persona, the safety report, automation and integrations, compliance and privacy pages, ops and diagnostics, knowledge and memory admin, telemetry (D32, with a random install id and no stored IPs; C4), and the one-click update through a separate updater container (G10). The page groups come from D49, D52 and D53. No separate "done when" is written in the spec; these tickets use: every D53 group has a page, every admin read of member data is audited (D59), and the updater never gives the app container Docker control.

What already exists and is built on here: the console shell, design system and admin pages from M2 to M6; the audit log; the admin read path (`src/data/admin-read.ts`); memories (M4-3); export and delete (M6-7); `morgan update` (M6-3); the socket proxy pattern (M3-7a); onboarding (M6-1).

## M9. Full console

### M9-1. Branding and the bot persona

- **Blocked by:** nothing in M9.
- **Demo:** the admin sets the bot's name, a short persona line and a logo; the web app header and the bot's greeting use them.
- **Tests first:** the persona text is a trusted admin setting placed in the system prompt below the safety rules, and a test proves it cannot remove or reorder them; a logo upload is size- and type-checked and stored in the file store; colours stay design tokens (no raw colour from the admin); screenshot tests in light, dark and right-to-left.
- **Work:** the settings (install-wide); the page; the prompt step.

### M9-2. The safety report

- **Blocked by:** nothing in M9.
- **Demo:** a page shows, per week, approvals asked, approved and denied, trust-check refusals with reasons, blocked actions per profile, and the latest holdout result per engine.
- **Tests first:** counts come from the audit log only (no new writes); no message content is shown, only types, counts and reasons; the latest release-gate result is read from a file the workflow publishes; Playwright and screenshot tests.
- **Work:** the summary query; the page.

### M9-3. Automation and integrations

D53: webhooks, API keys, n8n/Zapier, scheduled admin reports, settings import and export.

#### M9-3a. Outgoing webhooks

- **Blocked by:** nothing in M9.
- **Demo:** the admin adds a webhook for "approval asked" and "top-up requested"; each event posts a signed JSON body to the URL.
- **Tests first:** bodies carry ids and types, never message content (_proposed_, doubt 2); each post is signed with a per-webhook secret; retries with backoff and a dead-letter list on the page; the URL is checked against private ranges like the egress proxy (M3-8b).
- **Work:** the webhooks table (install-wide); the sender job; the page.

#### M9-3b. Scheduled admin reports

- **Blocked by:** M9-3a.
- **Demo:** the admin gets a weekly report in their chat: usage and cost per person, safety report numbers, backup status.
- **Tests first:** the report is a schedule owned by the admin (M4-4a) with a fixed template; it reads only aggregates; quiet hours apply.
- **Work:** the template; the setting.

#### M9-3c. Settings import and export

- **Blocked by:** M9-3b.
- **Demo:** the admin exports install settings as a JSON file and imports it on a second install.
- **Tests first:** the export holds settings, profiles, routes and workspace names, never credentials, users' data or the master key; import validates against the schema and shows a diff before applying; each import writes an audit row.
- **Work:** the export and import endpoints; the page. n8n and Zapier use the M6-5c API tokens plus these webhooks (doubt 3).

### M9-4. Compliance and privacy

#### M9-4a. Consent records and the notice editor

- **Blocked by:** nothing in M9.
- **Demo:** the admin edits the members' notice (what the admin can read, D59; telemetry once it ships); each person's acceptance of each notice version is recorded and shown.
- **Tests first:** a new notice version asks each person once at next sign-in or chat; acceptances are rows per person (RLS); the admin-read disclosure cannot be removed from the notice (a required block).
- **Work:** the notices and acceptances tables; the editor page.

#### M9-4b. The export and delete log, and legal hold

- **Blocked by:** M9-4a.
- **Demo:** the admin sees every export and deletion with date and the random tag, and can set or lift a legal hold on a person with a reason.
- **Tests first:** the log reads from the audit log; setting a hold blocks M6-7b's delete and says why; setting or lifting writes an audit row with the reason.
- **Work:** the page; the hold column.

### M9-5. Ops and diagnostics

#### M9-5a. Redacted logs and traces

- **Blocked by:** nothing in M9.
- **Demo:** the admin views recent structured logs filtered by level and module, with secrets and message content redacted.
- **Tests first:** the redaction runs before display and a fixture of known secrets and message text never appears; optional OpenTelemetry export goes only to the admin's own collector URL (spec L10).
- **Work:** the log view; the OTel setting.

#### M9-5b. Feature flags, rate limits, maintenance mode, version page

- **Blocked by:** M9-5a.
- **Demo:** the admin switches maintenance mode on and every chat gets "Morgan is under maintenance, back soon."; the version page lists the version, commit and lifted-code attributions from NOTICE.
- **Tests first:** maintenance mode queues turns rather than dropping them; rate limits are settings with bounds; flags are typed and listed in one place; the attribution page matches NOTICE (a test).
- **Work:** the settings; the pages.

### M9-6. Knowledge and memory admin

- **Blocked by:** nothing in M9.
- **Demo:** the admin opens a member's notes about them and reads them; the read is in the audit log, and the member can see that it happened.
- **Tests first:** every admin read goes through `src/data/admin-read.ts` and writes an audit row (D59, C10); the admin can delete a note only with a reason, audited; the member's own audit view shows admin reads of their data (_proposed_, doubt 4).
- **Work:** the page; the member's view of admin reads.

### M9-7. Telemetry

D32 and C4: opt-out, anonymous aggregates only, a random install id, no stored IPs, disclosed at onboarding.

#### M9-7a. The client side, off until disclosed

- **Blocked by:** the collection endpoint decision (doubt 1).
- **Demo:** after onboarding shows the telemetry notice, the install sends a weekly count of people, workspaces and features switched on, with a random id; the admin turns it off in one click.
- **Tests first:** the payload is a fixed schema of counts and booleans, snapshot-tested, with no names, emails, content, hostnames or keys; the id is random, created at setup, never derived from anything; nothing is sent before the onboarding notice step (M6-1c) has been shown; off means nothing is sent, tested with a fake endpoint; the notice is added to onboarding and to the notice editor.
- **Work:** `src/ops/telemetry.ts`; the setting; the onboarding step.

#### M9-7b. The collection endpoint

- **Blocked by:** M9-7a.
- **Demo:** a small endpoint receives the weekly payload, stores counts only, and drops the source IP before storage.
- **Tests first:** the handler never writes the IP or headers; a payload outside the schema is refused; a privacy notice page is served from the same host.
- **Work:** the endpoint (where it runs is the owner's call, doubt 1); the privacy notice.

### M9-8. One-click update through a separate updater

G10: the app never holds Docker control; a minimal updater container does.

#### M9-8a. The updater container

- **Blocked by:** nothing in M9.
- **Demo:** `compose.yaml` gains an `updater` service that, on a signed request from the app, runs the same steps as `morgan update`.
- **Tests first:** the updater accepts one request type (update to a named version) signed with a key only it and the app share; it reaches Docker only through the socket proxy with an allowlist of pull, stop, start and run of the stack's own images; the app container still has no Docker socket (the M3-7a compose test); a failed backup stops the update.
- **Work:** the updater image and service; the proxy allowlist for it.

#### M9-8b. The update button

- **Blocked by:** M9-8a.
- **Demo:** the update notice gets an "Update now" button; the admin confirms with their second factor; the page shows progress and the app comes back on the new version.
- **Tests first:** the button is admin-only and asks for a fresh second factor; progress is read from the updater's status; a failed update shows the rollback command; the action is audited.
- **Work:** the button and progress page. Closes A10.

### M9-9. The full console demo and the M9 report

- **Blocked by:** every ticket above.
- **Demo:** the owner walks every console group of D49, D52 and D53 and finds a page for each; updates the install with the button; reads a member's notes and sees the audit row; tag `v1.3.0`.
- **Tests first:** a test that lists the D53 groups and fails if any has no route in the console; Playwright smoke across every console page in light, dark and right-to-left.
- **Work:** the test; `docs/m9-report.md` in the shape of `docs/m1-report.md`: timings per ticket, spend, a page-by-page checklist against D49, D52 and D53.
- **Done when:** every console group has a page, every admin read is audited, the updater works without giving the app Docker control, and the report is merged.

## Doubts for the owner

1. **The telemetry endpoint.** C4: someone must run it, which makes the maintainer a data controller for EU installs. Where it runs and who pays is the owner's call; M9-7a ships off by default until then (_proposed_), which differs from D32's opt-out and needs the owner's word.
2. **Webhook bodies without content** _(proposed)_. Say if some events should carry text.
3. **n8n and Zapier.** No native app is proposed; they connect through API tokens and webhooks.
4. **Members seeing admin reads** _(proposed)_. D59 says each read is audited, not that the member sees it.
5. **Network and email settings** (D53) are only partly covered (SMTP in M8-3); a full page could be a tenth ticket.
6. **No "done when" in the spec for M9.** The tickets propose the one above.
