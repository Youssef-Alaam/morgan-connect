# Tickets: M6 (Operable by a stranger: v1.0)

Status: draft for the owner's review, 2026-11-28. Tickets are disposable: when the spec changes, close the unbuilt ones and regenerate.

Every ticket is a vertical slice: when it is merged, something new can be shown working. Every ticket follows `STANDARDS.md` (tests first, all CI checks green, one PR, at most 400 changed lines). "Tests first" lists the failing tests the builder writes before any code. A ticket too big for one PR is split into lettered parts (a, b, c), each its own PR of at most 400 lines, merged in order. Library names marked _(proposed)_ are not decided until the owner approves them.

Milestone goal (spec section 6): someone other than the owner installs it from the README alone on each of the three targets, and the release gate passes. Tagged **v1.0**. Contents: backups and restore (D33), the update command (D47, G10, A10), health page, security settings (force 2FA, revoke sessions, login history, API tokens; D52), models and tiers page, schedules overview, connectors catalogue, terms route table, export and delete (D48, A7, C9), install guides for VPS, Windows and Mac (D6, D51, G6), the Kubernetes plan document (D29), the minimum hardware spec (A6).

**Onboarding** has no ticket in any earlier milestone. The spec fixes its order (A11, review G4: setup code, admin account with 2FA and backup codes, safety model and first provider key, Telegram bot token and own chat, test message, backups offer, telemetry notice if it ships, then optional WhatsApp guide, connectors and invites; steps 1-5 under 15 minutes). It is placed here as M6-1, because a stranger cannot install from the README alone without it.

What already exists on `main` and is built on here: the setup code in the server log; admin accounts with password, TOTP, backup codes and passkeys; invites and temporary passwords; Telegram linking by code; the providers and channels page with the `routes` table; the atomic write helper. From M3 to M5 and a hard dependency where noted: the safety model required at setup (M3-3a), the terms policy file (M3-2a, M3-2b), the release gate (M3-12d), the credential vault and master key (M4-1), schedules (M4-4), connectors (M4-7 to M4-10), tiers (M5-2a), WhatsApp guide (M5-3d), workspaces (M5-5).

## M6. Operable by a stranger

### M6-1. First-run onboarding

Split into three PRs. A11 and review G4.

#### M6-1a. Steps 1 and 2: claim the install, admin account with 2FA

- **Blocked by:** nothing in M6.
- **Demo:** a fresh install's web page shows "Enter the setup code from the server log"; the right code leads to creating the admin with a password, an authenticator and backup codes; the wizard cannot be skipped and the code is dead afterwards.
- **Tests first:** Playwright on a fresh stack: the wizard is the only page reachable before setup finishes (every API route but the wizard's answers 403); a wrong code is rate-limited; the code works once; TOTP and backup codes are required for the first admin (story 1, story 14); the wizard's state survives a restart and resumes at the step reached; the time from page load to step 2 done is recorded.
- **Work:** `web/src/screens/setup/` steps 1-2 reusing the existing account and second-factor screens; a `setup_state` row (install-wide, exempt list); the API guard.

#### M6-1b. Steps 3 to 5: safety model and key, Telegram, a test message

- **Blocked by:** M6-1a, M3-3a, M4-1a.
- **Demo:** the wizard asks for the first provider key and the safety model, then a Telegram bot token, shows a link code for the admin's own chat, and finishes with "Send a test message"; the test message's reply shows in the wizard.
- **Tests first:** a key is checked by one cheap call before it is accepted, and a wrong key says why; the safety model must be on an allowed route; the bot token is checked with Telegram's `getMe` (recorded fixture); the step does not finish until the admin's own chat is linked and one test turn has answered; keys are sealed in the credential vault, never echoed back; the 15-minute target for steps 1-5 is measured in a Playwright run on the fake engine and the fake Telegram API (Morgan's own time only).
- **Work:** steps 3-5 screens; the checks in `src/http`.

#### M6-1c. Steps 6 to 8: backups offer, notices, optional extras

- **Blocked by:** M6-1b, M6-2a.
- **Demo:** after the test message, the wizard offers backups (daily, weekly or no), shows where the master key file is and tells the admin to store it separately, and ends on a page with optional links: WhatsApp guide, connect apps, invite people.
- **Tests first:** the backups offer sets the schedule from M6-2a and may be declined (D33); the master key warning names the file path (A8); the telemetry step is absent until telemetry ships (M9-7) and a test fails if a telemetry setting exists without its notice step; the members' disclosure that the admin can read chats is shown on the invite page (D59) and the test asserts it.
- **Work:** steps 6-8 screens; setup marked finished.

### M6-2. Backups and restore

Split into three PRs. D33: built-in, switchable, encrypted, a tested one-command restore.

#### M6-2a. Encrypted backups on a schedule

- **Blocked by:** nothing in M6.
- **Demo:** with daily backups on, a backup of Postgres and the files folder lands as one encrypted archive in the backup folder; `morgan backup now` makes one on demand.
- **Tests first:** the archive holds a `pg_dump` and the files store, encrypted with a backup key derived from the master key (_proposed_, doubt 1); the master key file itself is excluded by default and the archive's manifest says so (A8); a backup is written temp-then-rename and a half-written one is never listed; retention keeps the last N; the schedule runs as an install job and a failure is shown on the health page.
- **Work:** `src/ops/backup.ts`; the `morgan backup` CLI entry; the S3-compatible target as a port with the folder adapter only (doubt 2).

#### M6-2b. One-command restore

- **Blocked by:** M6-2a.
- **Demo:** `morgan restore <archive>` on an empty stack brings back every person, chat, memory and file, and the admin can sign in.
- **Tests first:** restore refuses a non-empty database unless `--force` is given, and says what would be lost; a wrong master key fails before anything is written; the restored database passes the migration check at the current version (an older archive is migrated forward); RLS still holds after restore (the isolation tests run on the restored database).
- **Work:** `src/ops/restore.ts`; the CLI entry; the restore section of the install guide.

#### M6-2c. CI restores the latest backup

- **Blocked by:** M6-2b.
- **Demo:** a CI job seeds a stack, backs it up, restores into an empty stack and runs the smoke test (spec section 7: "tested").
- **Tests first:** the job fails if any row count differs after restore, if a file's hash differs, or if the smoke test fails.
- **Work:** the job in `.github/workflows/ci.yml`; the seed script.

### M6-3. The update notice and `morgan update`

- **Blocked by:** M6-2a.
- **Demo:** when a newer release exists, the admin sees "Version 1.0.1 is available" in the console and in their chat once; `morgan update` backs up, pulls the images, runs migrations and restarts, and prints each step.
- **Tests first:** the check reads the public release feed at most once a day and sends no install data (no id, no counts; telemetry is M9); `morgan update` stops before pulling if the backup fails; a failed migration rolls back to the backup with one printed command; the update is the documented "notice plus one command" (A10, G10), and the app holds no Docker control for it.
- **Work:** `scripts/morgan` CLI subcommand; the version check job; the notice. Story 10.

### M6-4. The health endpoint and page

- **Blocked by:** nothing in M6.
- **Demo:** `/health` answers `ok` with the version; the console's health page shows the database, the queue, workers, each channel, the last backup, disk free and the container cap in use.
- **Tests first:** `/health` is public and leaks nothing but status and version; the page is admin-only (403 otherwise); each check has a time limit and a failed check shows red with one plain sentence; screenshot tests in light, dark and right-to-left.
- **Work:** `src/http/health.ts`; the page.

### M6-5. Security settings

Split into three PRs. D52.

#### M6-5a. Force 2FA and revoke sessions

- **Blocked by:** nothing in M6.

#### M6-5c. API tokens

- **Blocked by:** M6-5b.

- **Work:** the migration; token auth in `src/http/session.ts`; the page.

## Doubts for the owner

1. **Backup encryption key.** D33 says encrypted; A8 keeps the master key out of backups. M6-2a proposes a backup key derived from the master key, so a backup is useless without the separately stored key file. The alternative is a passphrase the admin types at setup. Say which.
2. **S3-compatible backup target.** D33 names it; M6-2a builds the port with the folder adapter only. S3 could be a second PR here or later.
3. **Login history and IPs** _(proposed)_: no IPs stored beyond the rate limiter's window. Say if the admin should see IPs.
4. **Strangers to test.** M6-8b and M6-10 need three people other than the owner, one per target. Who they are is the owner's call.
5. **Master key rotation** (M4 doubt 2) is not in the M6 list; it could join M6-5 as a fourth PR.
6. **Onboarding placement.** No milestone names onboarding; A11 fixes its order. It is placed in M6 because "installs from the README alone" needs it. Parts (steps 1-2) could move earlier if the owner wants strangers trying M4 or M5.
7. **v1.0 tag position** is the owner's to move (spec section 6).
