# Tickets: M2 (Many users)

Status: draft for the owner's review, 2026-11-26. Tickets are disposable: when the spec changes, close the unbuilt ones and regenerate.

Every ticket is a vertical slice: when it is merged, something new can be shown working. Every ticket follows `STANDARDS.md` (tests first, all CI checks green, one PR, at most 400 changed lines). "Tests first" lists the failing tests the builder writes before any code. A ticket too big for one PR is split into lettered parts (a, b, c), each its own PR of at most 400 lines, merged in order. Library names marked _(proposed)_ are not decided until the owner approves them.

Milestone goal (spec section 6): a second person and a restricted device use the same bot and cannot see or do what their profiles forbid; isolation tests pass.

What already exists on `main` and is built on here: `users`, `devices`, `workspaces` (one default workspace), `user_id` + `workspace_id` on every user-data table with a composite foreign key (migration 0010); the owner role that migrates and the app role that may only INSERT and SELECT on `audit_log` (`src/data/roles.ts`, ADR 0008); the `Untrusted<string>` type and wrapper (`src/safety/untrusted.ts`); the single policy gate with one hard-coded `OWNER_PROFILE` (`src/policy/`); the usage ledger and `/usage`; per-chat conversations with `/new`. M1-6 (approvals) is in progress and is a hard dependency where noted.

## M2. Many users

### M2-1. Row-level security as the second lock

Split into two PRs.

#### M2-1a. Every query runs as a person, and Postgres enforces it

- **Blocked by:** nothing in M2 (builds on migration 0010 and the app role).
- **Demo:** with two users in the database, a raw `select * from chat_messages` run through the app role returns only the rows of the user whose id is set on the transaction, and nothing when no user is set.
- **Tests first:** integration: with `app.user_id` and `app.workspace_id` set by the helper, the app role sees only that person's rows in `turns`, `chat_messages`, `chat_conversations`, `usage_ledger`; with nothing set it sees zero rows (fail closed, never all rows); an INSERT with another person's `user_id` is refused by the policy's `WITH CHECK`; a migration test lists every table in `public`, and fails if one is neither under an RLS policy (`relrowsecurity` and `relforcerowsecurity` on) nor named in the install-wide exempt list.
- **Work:** a migration that enables and forces RLS on each user-data table with one policy keyed on `current_setting('app.user_id', true)` and `app.workspace_id`; `withOwner(db, owner, fn)` in `src/data/` that opens a transaction and sets both values with `set_config(..., true)` (local to the transaction); every existing data function moved onto it; the exempt list (`workspaces`, `schema_info`, migration books, the pg-boss schema, and install-wide settings) as one exported constant the migration test reads. `audit_log` gets an RLS policy for SELECT only (INSERT stays open to the app role, because a refused stranger has no user). `users` and `devices` are read before a person is known (the unknown-sender gate, `ownerOf`), so they get a narrow policy for that lookup; the builder states the exact rule in the PR and the reviewer reads it line by line.
- **Out of scope:** the admin's read path (M2-2); the isolation-test checker (M2-1b).

#### M2-1b. An isolation test for every user-data table, checked by CI

- **Blocked by:** M2-1a.
- **Demo:** `node scripts/check-isolation-tests.mjs` lists each user-data table with the test that covers it, and fails when a new table has none.
- **Tests first:** unit tests for the checker: a fixture migration that adds a table with `user_id` and no matching isolation test makes it fail; an exempt table is skipped; a table named in a test file without an assertion on another user's rows still fails.
- **Work:** `scripts/check-isolation-tests.mjs` (STANDARDS step 14); one isolation test per user-data table, each proving user A cannot read or write user B's rows both through the data functions and directly under RLS; a shared test helper that seeds two users in two chats; the step wired into CI.
- **Done when:** CI step 14 is green and goes red when a sample table without a test is added in a throwaway commit.

### M2-2. The admin's read path is explicit and audited

- **Blocked by:** M2-1b.
- **Demo:** `adminRead.chat(admin, memberId, reason)` returns the member's chat, and the audit log shows who read whose chat, when and why; the same call from a member is refused and audited as refused.
- **Tests first:** the admin path returns the member's rows only after an audit row is written in the same transaction (if the audit insert fails, nothing is returned); a member calling it is refused with a typed error and an audit row; the normal `withOwner` path for the admin still shows only the admin's own rows (the admin sees members' data only through this path, never by accident); a read of memory rows goes through the same path (tested against the table once M4 adds it; until then, chats and usage only); an isolation-test helper `expectAuditedAdminRead(table)` that M2-1b's checker accepts as coverage of the admin rule.
- **Work:** `src/data/admin-read.ts` with one function per readable kind (chat, usage); an RLS policy branch that admits rows when `app.admin_read_of` is set, and that setting is only ever set inside this module after the audit insert; a lint or dependency-cruiser rule that nothing outside the module sets `app.admin_read_of`; the audit action type `admin.read`; the disclosure flag stored on the user (`told_admin_can_read_at`) that M2-5b sets at joining.
- **Out of scope:** the screen that uses it (M2-15d); memory (M4).

### M2-3. Idle gap starts a new session, and long sessions are compacted

Split into two PRs.

#### M2-3a. An idle gap starts a fresh conversation

- **Blocked by:** nothing in M2.
- **Demo:** after the idle gap (default 6 hours, set by config) the next message starts a new conversation, as if the person had typed `/new`, and the reply says so in one short line.
- **Tests first:** with fake timers, a message just under the gap continues the conversation and one just over it starts a new one; the old conversation is ended on the engine (`Engine.end`) exactly once; a turn still running when the gap passes is not cut; the gap is read from config, and a value under 5 minutes is refused at boot.
- **Work:** `IDLE_GAP_MINUTES` in the config schema; the check at turn start in `src/core`; reuse of the existing `/new` path.

#### M2-3b. Compaction before the context fills

- **Blocked by:** M2-3a.
- **Demo:** in a long conversation, once history passes the threshold, the oldest part is replaced by a short summary, and the reply carries on without losing the thread.
- **Tests first:** on the scripted fake engine, history over the threshold (in tokens, from the engine's `usage`) is compacted once, and history under it never is; the summary row is stored with the range of messages it replaced, and those rows are kept, not deleted; tool calls and their results are never split across the cut (the history stays well formed, as #39 requires); the summary is marked as Morgan's own text, and any user or tool text inside it stays `Untrusted`; a compaction call is a model call and writes a usage-ledger row.
- **Work:** compaction lifted from Nod (licence header kept, change marked in `NOTICE`); a `summary` role or flag on `chat_messages`; the threshold in config. A hook point named `beforeCompact` that M4's memory rule (story 19: offer to keep what matters before old context is dropped) will use; in M2 it does nothing.
- **Out of scope:** the memory offer itself (M4).

### M2-5. Accounts: invite link and temporary password

Split into two PRs.

#### M2-5a. Web accounts and sessions

- **Blocked by:** M2-1a.
- **Demo:** the admin, claimed through the setup code, sets an email and password from a one-time link printed in the log and signs in to `/api/me`, which returns their user and workspace.
- **Tests first:** integration over the HTTP API: sign-in with the right password returns a session cookie (HttpOnly, Secure, SameSite=Lax) and a wrong one is refused and rate-limited; `/api/me` without a session is 401; the session maps to the existing `users` row and its workspace, and every API handler runs inside `withOwner`; passwords are never logged (logger fixture test); the admin's first-password link works once and expires.
- **Work:** Better Auth _(proposed)_ mounted on Hono in `src/http`, with its tables in `src/data` migrations, linked one to one to `users`; a web session counts as a device (A1) in `devices` with channel `web`; the session middleware.

#### M2-5b. Invite link and temporary password

- **Blocked by:** M2-5a.
- **Demo:** the admin creates an invite with a role and a monthly limit through the API; the person opens the link, sees the notice that the admin can read their chats and memories (D59), sets a password, and is signed in. The admin can instead create an account with a temporary password, which must be changed at first sign-in.
- **Tests first:** an invite link works once and dies when the account is created (D11); it expires; its token is stored hashed; the role and limit on the invite land on the new user; joining is refused until the notice is accepted, and acceptance sets `told_admin_can_read_at`; a temporary-password account can call nothing but "change password" until it does; only the admin can create invites or accounts (policy test, audit row).
- **Work:** `invites` table (install-wide or per workspace, keyed for RLS); the endpoints; the disclosure text as a translation key. The screen is M2-15a.

### M2-6. Password plus authenticator plus backup codes

### M2-8. Link a chat to an account by code

- **Blocked by:** M2-5b.
- **Demo:** a signed-in member asks the web app for a link code, sends `/link <code>` to the Telegram bot, and that chat becomes one of their devices; a chat that is not linked still gets no reply at all.
- **Tests first:** a link code works once, expires after 10 minutes, and is stored hashed; a wrong code is refused and rate-limited per chat; the new device belongs to the member who asked for the code, never to the admin; a chat already linked to another person cannot be taken over by a new code; the unknown-sender gate is unchanged (no turn for an unlinked chat); linking and unlinking each write an audit row.

### M2-9. Access profiles per user and device

Split into two PRs.

#### M2-9a. Three presets, stored and assigned

- **Blocked by:** M2-8.

- **Tests first:** the generated table test over every (preset, action type, device kind) cell, built from the `ActionType` union (STANDARDS section 3), so a new action type with no row is a compile error; Restricted is `read` auto and every other type off (D31); a device profile overrides the person's, and a device with none takes the person's; every grant that loosens a type returns its risk warning (D27); changing a profile writes an audit row; each profile carries its shell-gate level, default risky-only (D30, D61), stored now and used in M3.
- **Work:** `access_profiles` and `profile_assignments` tables; the three presets as seed rows; `profileFor(user, device)` in `src/policy`. Preset values for Standard and Trusted are proposed by the builder in the PR as a table for the owner to sign (see doubts).

#### M2-9b. The gate uses the profile, and a blocked action says so

- **Blocked by:** M2-9a, M1-6.

- **Tests first:** the policy gate decides from `profileFor(user, device)` and no longer from `OWNER_PROFILE`; an `off` decision returns a plain, fixed sentence to the user and never a silent failure (story 27), and the model is told it was refused; an `ask` decision on a member's device sends the approval to that member, not the admin (D19); the restricted-device bypass cases from spec section 7 (rephrasing, asking the model to call the tool another way, a tool that declares a lower action type) are each refused; every decision still writes one audit row.
- **Work:** the gate change in `src/policy/gate.ts`; `OWNER_PROFILE` removed; the "switched off" message as a translation key.
- **Out of scope:** the admin taking over approval for chosen people or actions (story 6; see doubts).

## Doubts for the owner

1. **No brand inputs exist yet.** `docs/brand.md` is not in the repo (M0-6 is still open), and no colour, font or logo values are recorded in the decision log. M2-13a therefore ships a neutral placeholder palette and system fonts, clearly marked. Missing: the palette as named light and dark tokens, the two fonts (and their licences, which must be on the STANDARDS allowlist), the logo mark (favicon and avatar sizes), and any spacing or radius preferences. When the design tool produces them, one PR swaps the token file.
2. **Token-only lint, screenshot tests and accessibility tests are "proposed additions" not yet approved** (STANDARDS status line, 2026-11-25), but spec section 7 and D63 require them. M2-13 assumes the owner approves them; otherwise drop those test lines.
3. **Better Auth is proposed, not decided**, and it brings its own user and session tables. The tickets link them one to one to the existing `users`; the owner may prefer another library.
4. **Preset values for Standard and Trusted** are not in the spec (only Restricted is defined, D31). M2-9a asks the builder to propose a table for the owner to sign.
5. **Admin taking over approvals for chosen people or actions (story 6, D19)** is not in the M2 list in spec section 6, and the approvals inbox is M3. Left out of M2; say if it belongs here.
